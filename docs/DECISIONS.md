# Design Decision Log

更新日：2026-10-17

| ID | 決定 | 理由 | 見直す条件 |
|---|---|---|---|
| D01 | 製品はLiving / Inspect / Labを持つ統合コンセプト | 観測から理解へ移る体験を分断しない | 利用者検証で独立製品が優れると判明 |
| D02 | MVPはCPU活動量・競合のみ | 一つの現象で体験の価値を検証できる | MVP完了後 |
| D03 | Rustの3 crate，1プロセス | CLIとGUIの再利用性と単純さを両立 | 明確な独立配布・共有要件が発生 |
| D04 | Sceneは意味的モデル，RendererはTUI固有 | 将来GUIに共通化しやすい | 実装で抽象化が過剰と判明 |
| D05 | Living / Metrics / Splitの3表示 | 比喩と数値の対応が製品価値 | 利用者テスト |
| D06 | 仕事の山はCPU PSIに基づく比喩 | PSIは待機タスク数でないため | 実トレースによる正確なタスク表現を追加 |
| D07 | PSI `full`（system level）は使用しない | カーネル定義上の制約 | 対象スコープをcgroup等に拡張 |
| D08 | Agent，GUI，Simulation，record/replayを後回し | MVPの過剰実装を回避 | 必要な利用体験と実装検証が明確になった段階 |
| D09 | CoreはOS・描画技術非依存 | 同じ意味モデルを複数UIで再利用する | 導入コストが便益を超える場合 |

## 未決事項（MVP実装中に検証）

- Sceneの平滑化・ヒステリシス係数と山の段階しきい値．
- Split Viewのレイアウトと最小端末サイズ．
- メモリ・I/O・ネットワークを追加するときの一貫した世界観．
- 記録・再生時のスキーマとセッション時間管理．
- GUIの実装技術（現時点の候補はTauri）．
- 観測スコープとしてcgroup/コンテナをどう扱うか．

## v0.1の操作・終了処理の改善

| ID | 決定 | 理由 | 見直す条件 |
|---|---|---|---|
| D12 | `i`で同じ観測の詳細，`?`でヘルプを表示し，詳細は開いたsample_idに表示固定する | 別のinspectコマンドで再計測すると短縮された元の欠測原因を失うため．計測と履歴は継続する | 利用者評価で読み方・戻り方が分かりにくい場合 |

## 利用者評価を受けたライブ中心の改訂（2026-10-18）

D10・D12の画面・詳細表示方針を以下で更新する．解析式・Sceneの意味・依存方向は維持する．

| ID | 決定 | 理由 | 見直す条件 |
|---|---|---|---|
| D14 | 引数なしでSplitのライブ監視を開始．単発status／inspectを廃止し，JSONもNDJSONストリームにする | 継続する状態変化を読む監視体験が必要との利用者指摘 | 明確な単発出力の利用要求がある場合 |
| D15 | PCキャラクターをUnicodeと色で描き，余白を確保．80×24では横並び，狭い画面は縦並び | 旧表示はキャラクターが小さく，文字の説明が画面を占有していた | 実端末での見え方・操作評価 |
| D16 | 通常画面は現在値・グラフ・比喩に絞る．sample_id・取得元・計算式・理由全文はi，意味と操作は? | 技術説明や山のラベルが視認性を損なっていた | 指標の誤読が起こる場合 |
| D17 | 詳細も最新観測へ追随する | 監視はライブを基本とする要求に合わせる．同じAnalysisから根拠を生成 | 読取り中の固定が明確に必要になった場合 |

JSONの各レコードのschema_versionは1を維持する．内容の構造は維持するが，出力は単独の整形済み文書から1行1レコードの継続ストリームへ変わる．正式公開前のCLI変更であり，READMEの利用手順も更新する．

## 普通のPC・英語UI・短い指標名への改訂

| ID | 決定 | 理由 | 見直す条件 |
|---|---|---|---|
| D22 | ロボットを通常のモニター・スタンド・キーボードへ変更．顔を含めて対称にする | 利用者が普通のPCの表現を希望．前回の対称性検証は顔を対象に含めていなかった | 実端末・利用者評価 |
| D23 | UI・CLIヘルプ・診断説明を英語へ統一．View: Computer / Charts / Both | LivingとSplitでは選択対象と同時表示が伝わらなかった | 利用者評価 |
| D24 | CPU usage / WorkingとCPU wait / Waiting for CPUを対にする | 活動量と競合の違いを名称と配置で直接伝える | 指標の誤読が発生した場合 |
| D25 | 詳細は値と短い定義，PSIの正式名とWindowの意味だけに絞る．式と差分はJSONへ | 技術用語・長い読み方・重複した説明が視認性を損なった | 必要な情報へ到達できない場合 |

CPU usageは既存のcpu_active_ratioのUI上の名称であり，計算式は変更しない．I/O waitとstealを活動に含めない近似値であることを詳細とREADME，完全な式をNDJSONと設計文書に保持する．CPU waitはPSI someの時間割合であり，I/O待ちや待機タスクの個数には変換しない．

## 短いスタンド・待ち時間の具体化・README動画

| ID | 決定 | 理由 | 見直す条件 |
|---|---|---|---|
| D26 | スタンドの首を1行短くする．キーの点灯と消灯に明暗を付ける | PCらしい比率を保ち，CPU usageに応じたキーの点滅を認識しやすくする | 実端末の見え方 |
| D27 | 詳細へWait time（直近の観測時間内にCPUを待ったms）だけを追加 | PSIの割合を具体的な時間へ結び付ける．既存のsome.total差分をmsへ換算し，独立した計測・個数の推定は増やさない | 理解度評価 |
| D28 | PSIはLinuxのCPU待ち時間の計測と説明．10s trendはrecent CPU wait，WindowはUpdatedへ | 正式名称や抽象的な読み方だけでは意味が伝わらなかった | 利用者評価 |
| D29 | READMEで高使用率・低競合と高使用率・高競合のGIFを比較する | CPU usageとCPU wait，キーの点滅と書類の違いを実際のRendererの画像で伝える | 表示変更時 |

新しいリソースや生カウンタは追加しない．Wait timeは解析が有効な区間に限り表示し，初回・欠測・不正時は0で補わない．GIFは同一fixture観測のまま描画時刻だけを進めた合成例で，実機負荷実験ではない．Pillowは任意の開発用画像書出しにだけ使用し，アプリやCIの依存は増やさない．

## PC本体での忙しさと落ち着いた表示例

| ID | 決定 | 理由 | 見直す条件 |
|---|---|---|---|
| D30 | キーボードを撤去し，PC本体の画面・筐体色，表情，汗でCPU usageを表現 | キーの点滅では忙しさが伝わりにくく，重複する表現が不要という利用者指摘 | 実端末・利用者評価 |
| D31 | READMEにC（8%・wait0.1%）を追加し，A/Bの比較GIFも更新して維持 | 忙しくない状態と，高使用率の低競合／高競合を見比べられるようにする | 描画変更時 |

色は既存のScene表示強度で緑から暖色へ連続変化し，70%以上では汗を描く．これは描画上の比喩で，温度や異常の判定ではない．PSIは書類のみに対応させる．0と欠測で汗を発生させず，欠測は灰色・?で落ち着いた状態と区別する．PCの占有領域を39×12へ縮め，余白と80×24未満のサイズ案内を維持する．計測・解析・依存方向は変えない．

## 汗の動きと忙しい表情

| ID | 決定 | 理由 | 見直す条件 |
|---|---|---|---|
| D32 | 汗は小さな青いしずくを左右別の周期で下へ流し，消えてから再出現させる．忙しい口は笑顔から下向きへ変える | 対称な点滅と笑顔では忙しさが伝わらなかった．顔・PC本体の対称性は維持する | 実端末・利用者評価 |
| D33 | CPU waitの%表示を維持する | PSI someは少なくとも1タスクがCPUを待った時間の割合．1秒中280msなら28%であり，CPU使用率やタスク数とは異なる | 指標の誤読が発生した場合 |

単位の根拠は[Linux PSI仕様](https://docs.kernel.org/accounting/psi.html)．区間割合の計算・欠測処理・Sceneの意味は変更しない．
