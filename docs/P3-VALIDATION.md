# P3 検証・磨き込み

検証日：2026-10-18．対象：P0〜P2の取得・解析・Scene・CLI/TUI．

## 完了範囲と検証の限界

合成fixtureによる数値と比喩の対応，しきい値境界，平滑化応答，端末サイズごとの表示内容を検証した．実PTYでは通常の/proc観測のみを使い，キー操作・リサイズ・端末復旧を検証する．高負荷ワークロードの自動起動はテストにも補助スクリプトにも含めない．

**実機の高活動・低競合／高競合の比較実験と，利用者による理解度評価は未実施**．制限環境の指定がないため，この作業環境を負荷実験の対象にはしない．以下の合成データを実機測定結果として扱わず，暫定しきい値の運用上の妥当性や製品仮説の検証済みを意味しない．

## ケースA〜D：取得から画面まで

入力は`apps/inside/tests/fixtures/p3`．CPU累積値・PSI totalの前後差分と，単調時計に由来する1秒の観測区間を与え，Linuxパーサ → Core解析 → Scene → Ratatui TestBackendまで同じ経路を通す．フィクスチャの時刻も合成値．`procs_running`は全ケース2に固定する．

| ケース | CPU活動量 | PSI some区間割合 | 表示強度（初回の正常値） | 山 | 判定 |
|---|---:|---:|---:|---|---|
| A：高活動・低競合 | 93% | 0.2% | 93% | `[.....] 0/5` | 活発，山は低い |
| B：高活動・高競合 | 92% | 28% | 92% | `[#####] 5/5` | 活発，山は高い |
| C：低活動・低競合 | 8% | 0.1% | 8% | `[.....] 0/5` | 活動は小さく，山も低い |
| D：PSIファイル欠測 | 85% | N/A | 85% | `[?] 不明` | 活動を維持し，山は不明 |

AとBはCPU活動量の差が1ポイントでも山を0／5として区別できた．runnable参考値が同じでも山が異なることを確認し，待機タスクの個数への変換がないことも確認した．LivingとMetricsと履歴の最新sample_idはすべて2．初回は差分なしとして履歴に`?`を残す．

Dと長いI/Oエラーでは，N/Aと理由コードが見え，正常なCPU指標・他の参考値・履歴が押し出されないことを確認した．既存の山5から欠測に変わった後も，リサイズで以前の山が残らない．完全な原因メッセージは`inspect cpu`とJSONに保持する．

## しきい値・平滑化・アニメーションの評価

- CPU PSIの比喩段階は0.5%，2%，5%，10%，25%の5境界．各境界の直前・一致・直後をテストし，一致時は上の段階になることを確認済み．0%は段階0，100%は段階5，欠測・範囲外・非有限値は不明．A〜Dを区別する最小の暫定ルールとして維持する．実機データの裏付けなしに「適切に校正済み」とせず，しきい値は変更しない．
- ヒステリシスはないため，例えば0.49%／0.51%の往復で山は0／1を往復する．この感度をテストと本報告で明示する．実機で目立つちらつきがある場合に，実測値を変えずScene側だけの対策を判断する．
- 活動強度のEMAはα=0.5．0→100%のステップで，表示強度は50%，75%，87.5%，93.75%，96.875%となる．約1Hz観測なら約5秒で目標値の約97%へ到達する．瞬時値と表示強度の遅れは意図した表示処理であり，両者を別ラベルで表示する．欠測では過去値を残さず，復帰時は現在値から再開する．
- キャラクターの動作位相はRendererが持ち，表示強度に応じて変わる．仕事の山はSceneの段階だけで決まり，描画フレームで勝手に増減しない．欠測と表示強度0ではキャラクターは動かない．
- 履歴は共通の0〜100%スケール．0.1%と0.2%のような小さい差は同じ棒になるため，小さい差は数値で読む．山の段階はPSI区間割合に基づき，avg10は平滑化された傾向として併記する．

## 端末サイズの評価

| サイズ | Splitの配置 | 内容検証 |
|---|---|---|
| 140×34，120×32 | 横並び | PC，山，主要4指標，理由，履歴，観測区間，注記が見える |
| 100×24 | 横並び | 同じ必須情報を維持する |
| 80×24，60×24，40×24 | 縦並び | 各8行に圧縮し，PC・山・履歴も省略しない |
| 幅40未満または高さ24未満 | 選択モードの簡略表示 | キー操作を優先し，表示できる行数内で値と不明理由を表示する |
| 1×1，0×0 | 極小・非表示 | panicしない．十分な大きさへ戻すと再描画できる |

40×24以上を，全3表示で主要情報を読める検証済みの最小サイズとする．それ未満で全情報を同時表示することは保証しない．長い文は表示セル幅で`…`に省略し，折返しで後続の情報を隠さない．長い理由は`i`で同じsample_idの全文を確認する．別コマンドの`inside inspect cpu`は新しく観測する．

合成画面の保存物は[validation](validation/README.md)を参照．文字セル・レイアウトの評価であり，日本語フォントの見え方，色覚・端末配色，利用者の理解度までは評価していない．

## 制限環境での手動負荷検証（未実施）

これは人が専用環境で行う手順であり，自動テストやCIへ組み込まない．

1. 専用Linux VMに2 vCPUを割り当て，ホスト側でもそのVMのCPU上限を2 vCPU分に制限する．共有・業務環境を使わない．観測対象はVM内のsystem-viewとする．コンテナのCPU制限だけで，その/procがホスト全体を表示する場合はこの比較に使用しない．
2. VMのCPU一覧が0，1で，通常のrunnable・PSI取得が可能なことを確認する．kernel，VMの割当，CPU affinity，ツールのバージョンを記録する．PSI未対応なら未対応として記録し，比較成立としない．
3. VM内でビルドを済ませ，`inside live`を80×24以上の別端末で開始する．負荷中にはコンパイルをしない．通常状態のJSONと画面を記録する．
4. ケースAを人が1回起動する．起動直後の数秒を避け，別端末で`inside status --json`を5回程度手動実行し，出力を個別に保存する．終了を確認してから次へ進む．
5. ケースBを人が1回起動して同様に記録する．同じVM・affinity・時間制限を使う．終了後に通常状態へ戻ったことを確認する．
6. A/Bとも高活動になったか，CPU活動量が同程度か，BのPSI区間割合がAより大きいかを複数観測で比較する．条件が作れていなければ「比較条件未成立」と記録し，成功したことにしない．avg10の遅れは区間割合と別に読む．
7. Living／Metrics／Splitを切り替え，山の意味が競合の段階として理解できるか，対応する数値とsample_idを追えるか，初回・欠測をゼロと誤読しないかを利用者に確認する．

`stress-ng`を事前に用意した専用VMでの手動起動例（両ケースを同時に実行しない）．負荷はCPUのみ，各15秒，外側のtimeoutも設定する．このコマンドは今回実行していない．

```sh
# A: 2 vCPUに2 workers．比較条件が成立するかは実測で判断する．
timeout --signal=TERM --kill-after=2s 20s taskset -c 0,1 stress-ng --cpu 2 --cpu-load 100 --timeout 15s --metrics-brief

# A終了確認後，B: 同じ2 vCPUに8 workers．
timeout --signal=TERM --kill-after=2s 20s taskset -c 0,1 stress-ng --cpu 8 --cpu-load 100 --timeout 15s --metrics-brief
```

`--cpu`のworker数・`--cpu-load`・`--timeout`の定義は[stress-ng公式マニュアル](https://github.com/ColinIanKing/stress-ng/blob/master/stress-ng.1)を参照．負荷ツール自身の終了猶予があるため外側のtimeoutも用いる．実際の活動量・競合の値や特定の段階になることは保証しない．

記録用の項目：日時／実行者／VM・kernel／制限設定／ケース／CPU活動量／PSI区間割合／avg10／山の段階／sample_id／画面サイズ／理解できた点・誤読／判定と根拠．実測結果の記入欄は現時点で未記入とする．
